How this works — balances, sources, risk logic

What this is. A demo of an agentic treasury tool: the agent watches every rail (bank accounts, exchange balances, wallets) against a liquidity policy, proposes rebalancing transfers, and stops at the decision — you approve or reject. Everything runs in your browser and is saved locally; it starts with simulated data so you can play immediately.

Where balances come from. Each rail has a source, set under configure: simulated (demo), on-chain (live public balances of watch addresses — BTC via mempool.space, USDT TRC-20 via TronGrid; just paste addresses, no credentials), or manual (a number you maintain). Private exchange APIs (Kraken, Binance) need credentials and are only supported in the self-hosted version — API keys should never touch a public web page.

When is a rail at risk. You set min / target / max per rail. Below min = low: operations that depend on that rail can stall. Above max = excess: overexposure to one counterparty. The agent proposes transfers back to target through whitelisted corridors only, never drawing a donor below its own target; what it can't solve within policy it escalates to you. It never executes — approvals just record an instruction.
